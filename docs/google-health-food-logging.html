Managing your food logs from the CLI

Logging food is a write operation, and that changes the answer completely. The Health Connect export route is out (read-only). Everything now hangs on one awkward gap.

The gap, stated plainly

The Google Health API does support creating food logs — POST /v4/users/me/dataTypes/nutrition-log/dataPoints with the nutrition.writeonly scope. But no CLI or MCP tool exposes it yet. I checked the official CLI's source: nutrition-log is registered with operations list, get, rollup, daily-rollup, reconcile — no create. Only six types are writable there, and food isn't one of them.

// pkg/types/registry.go:508 — google-health-cli @ main register(&DataType{ ID: "nutrition-log", FilterName: "nutrition_log", TimeField: interval, Category: "nutrition", Description: "Logged food/nutrition entries with nutrient and energy breakdown", Operations: []string{"list", "get", "rollup", "daily-rollup", "reconcile"}, // ← no "create" })
So the working setup is a hybrid: let ghealth own the OAuth and token refresh, borrow its access token, and curl the write endpoint yourself. About 20 lines of shell. You get scriptable logging today without waiting for the CLI to catch up.

The hybrid chain

The point of this shape: OAuth refresh is the genuinely annoying part, and ghealth already solves it. You only bypass it for the one call it can't make.

Step 1 — get a token that's allowed to write

Undocumented

ghealth's interactive scope picker only offers read scopes — its AllScopes list contains nothing but .readonly. But --scopes is an unvalidated passthrough: it splits on commas and hands each value straight to the OAuth config, and FullScope() prefixes bare suffixes. So you can request the write scope anyway.

# request nutrition read + write; --scopes bypasses the readonly-only picker ghealth auth login --scopes "nutrition.readonly,nutrition.writeonly" # confirm what the token actually carries ghealth auth status ghealth auth export | jq -r '.scopes[]'
I could not run this. It's read off cmd/auth.go:164-172 and pkg/auth/auth.go:80-89, not executed — no Google Health account in this session. If the picker rejects it, fall back to your own OAuth client and a plain curl token exchange.
Adding a scope invalidates the old token. The write scope requires fresh consent — an existing read-only refresh token will not silently gain it.

Step 2 — the POST

Two ways to log a meal, and the choice has a real consequence.

Anonymous food

not editable

You supply the name and every number yourself. Simplest to script — no catalog lookup — but the entry is frozen once created. Wrong macros means delete and re-log.

{ "nutritionLog": { "interval": { "startTime": "2026-09-22T12:30:00Z", "endTime": "2026-09-22T12:30:00Z" }, "foodDisplayName": "Chicken burrito", "mealType": "LUNCH", "energy": { "kcal": 650 }, "totalCarbohydrate": { "grams": 72 }, "totalFat": { "grams": 24 }, "nutrients": [ { "nutrient": "PROTEIN", "quantity": { "grams": 38 } } ], "serving": { "amount": 1.0 } } }

Identified food

editable · preferred

Reference a catalog food and the API fills in every nutrient for you. Entries stay editable. Costs you a lookup — and the food has to exist in the catalog.

{ "nutritionLog": { "interval": { "startTime": "2026-09-22T12:30:00Z", "endTime": "2026-09-22T12:30:00Z" }, "food": "users/me/dataTypes/food/dataPoints/<id>", "mealType": "LUNCH", "serving": { "amount": 1.0 } } }

Find IDs with ghealth data food list (needs nutrition.readonly). Build yourself a local alias file of the ~30 foods you actually eat and you never do a lookup again.

# the call itself curl -sS -X POST "https://health.googleapis.com/v4/users/me/dataTypes/nutrition-log/dataPoints" \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d @meal.json

mealType: BREAKFAST · LUNCH · DINNER · SNACK · MEAL_TYPE_UNSPECIFIED. Every nutrient quantity is in grams; energy is kcal. Returns a long-running Operation, not the created object.

Step 3 — the wrapper that makes it a one-liner

This is the piece that turns the whole thing into something you'd actually use daily. ghealth auth refresh keeps the token alive, so the script never deals with OAuth itself.

#!/usr/bin/env bash # flog — log a meal to Google Health # usage: flog lunch "Chicken burrito" 650 72 24 38 # meal name kcal carb fat protein set -euo pipefail meal="${1:?usage: flog <breakfast|lunch|dinner|snack> <name> <kcal> [carb] [fat] [protein]}" name="${2:?missing food name}" kcal="${3:?missing kcal}" carb="${4:-0}"; fat="${5:-0}"; prot="${6:-0}" # ghealth owns the refresh cycle; we just borrow the current access token. ghealth auth refresh >/dev/null tok=$(ghealth auth export | jq -r .access_token) now=$(date -u +%Y-%m-%dT%H:%M:%SZ) jq -n --arg n "$name" --arg t "$now" \ --arg m "$(printf '%s' "$meal" | tr '[:lower:]' '[:upper:]')" \ --argjson k "$kcal" --argjson c "$carb" \ --argjson f "$fat" --argjson p "$prot" ' { nutritionLog: { interval: { startTime: $t, endTime: $t }, foodDisplayName: $n, mealType: $m, energy: { kcal: $k }, totalCarbohydrate: { grams: $c }, totalFat: { grams: $f }, nutrients: [ { nutrient: "PROTEIN", quantity: { grams: $p } } ], serving: { amount: 1.0 } } }' \ | curl -sS -X POST \ "https://health.googleapis.com/v4/users/me/dataTypes/nutrition-log/dataPoints" \ -H "Authorization: Bearer $tok" \ -H "Content-Type: application/json" \ --data-binary @- | jq .

Then it's just: flog dinner "Pad thai" 820 96 30 34. Wrap that in fzf over a TSV of your regular meals and logging becomes two keystrokes.

Reading it back — this part is easy

Everything on the read side is already covered by the official CLI, no wrapper involved.

ghealth data nutrition-log list --format table ghealth data nutrition-log daily-rollup # daily calorie/macro totals ghealth data nutrition-log list --format csv > food.csv ghealth data food list # catalog, for identified-food IDs ghealth data nutrition-log list --raw --limit 1 # ← confirm the real JSON shape
Do that last one first. Google's own docs disagree with themselves on the NutritionLog shape — the nutrition guide shows interval, the RPC reference shows sample_time / notes / serving[]. A real response settles it. Log one meal in the Google Health app, read it back raw, and mirror that exact structure.

Things that will bite you

Refresh tokens die every 7 days while the OAuth consent screen is in Testing. For daily food logging that's fatal. Push the project to In Production before you build any habit on this — then tokens last until revoked.
Anonymous entries can't be edited — only deleted, and only via :batchDelete (there is no HTTP DELETE). Typo a calorie count and you delete and re-log. Hydration entries, by contrast, are fully mutable via PATCH.
The food catalog is the weak spot. Users report it's thin compared to MyFitnessPal-class databases. Budget for mostly-anonymous logging, or keep your own local food table and push anonymous entries from it.
Writes need no Fitbit. Unlike the read side, food logging doesn't depend on owning a wearable — it's your Google account's data store. Nothing to buy.

Suggested order of work

  1. Prove the shape before writing code. Log one meal in the Google Health app, then ghealth data nutrition-log list --raw --limit 1. That single response resolves the docs contradiction and gives you a template to mirror.
  2. Publish the OAuth consent screen to In Production immediately — otherwise you re-consent every 7 days and the automation is dead on arrival.
  3. Get the write scope via ghealth auth login --scopes "nutrition.readonly,nutrition.writeonly". If that's rejected, stand up your own OAuth client and do the token exchange with curl.
  4. Then the wrapper. Start anonymous-food — it needs no catalog and covers the automation case. Add identified-food lookup later only if you want editable entries.
  5. Consider upstreaming it. nutrition-log only needs "create" added to its Operations list in pkg/types/registry.go; the generic data … create --json path already exists. That's a small PR against an official Google repo with 7 commits on main.
