fsync · sync model

What happens when you create a food log

Short answer: nothing, until you push. Writing a file only changes your disk. fsync notices it because it has no id, and push is the only command that ever writes to Google — creating, replacing and deleting alike. fsync add is just this flow with the file written for you.

Step by step

You want to log a burrito you ate at 12:30 today.

1

You write a file

Anywhere under food/, any filename. Four fields are required; everything else is optional.

# food/whatever.md — the name genuinely does not matter --- meal: LUNCH name: Chicken Burrito start: '2026-09-23T12:30:00-07:00' kcal: 650 carbs_g: 72 --- Ate half of it.

No id field. That absence is the entire signal — it's what makes this a create rather than an update.

2

fsync status sees it

Every .md under food/ is read at any depth, and sorted by what its frontmatter says — never by where it sits or what it's called.

$ ./fsync status new whatever.md -> will be created status 20 in sync, 0 modified, 1 new, 0 awaiting pull, 0 unreadable
3

fsync push sends it

Validation first, locally: meal must be a real meal type, kcal must be a number, the four required fields must be present. A bad file is reported and skipped — it never reaches the network.

Then the token: ghealth auth refresh runs, and the access token is read out of ghealth auth export. fsync never handles OAuth itself.

POST https://health.googleapis.com/v4/users/me/dataTypes/nutrition-log/dataPoints {"nutritionLog": { "interval": { "startTime": "2026-09-23T19:30:00Z", "endTime": "2026-09-23T19:31:00Z", "startUtcOffset": "-25200s", "endUtcOffset": "-25200s" }, "mealType": "LUNCH", "foodDisplayName": "Chicken Burrito", "energy": { "kcal": 650, "userProvidedUnit": "CALORIE" }, "totalCarbohydrate": { "grams": 72 }, "serving": { "amount": 1, "foodMeasurementUnitDisplayName": "serving" } }}

Your local time became a UTC instant plus an offset, because that's the shape the API actually returns. The body of your file — "Ate half of it" — is not in the payload. Notes stay on your machine.

4

The file rewrites itself

On success, the returned id goes into the frontmatter, a sync digest is recorded, and the file moves to its canonical home.

$ ./fsync push ok 2026-09-23/1230--chicken-burrito--884…201.md created # food/2026-09-23/1230--chicken-burrito--884…201.md --- id: '8841002938471100201' ← new: the join key meal: LUNCH name: Chicken Burrito start: '2026-09-23T12:30:00-07:00' kcal: 650 carbs_g: 72 sync: pulled: '2026-09-23T12:31:04-07:00' digest: 7b21c0aa91e4f033 ← how later edits are detected --- Ate half of it. ← your notes survive

The entry is now indistinguishable from one that was pulled down. The next pull matches it by id and reports it unchanged.

Editing: replaced, not patched

Edit the frontmatter of a synced file and push. The entry is replaced — a new one created, the old one deleted — so it comes back with a new id, and the file is renamed to match.

$ ./fsync status edit 2026-09-23/1558--black-sesame-soymilk--8889828334113072990.md -> replaced remotely; gets a new id $ ./fsync push ok 2026-09-23/1558--black-sesame-soymilk--3843781039477682293.md replaced 8889828334113072990

Same file, same content, different id — and a different filename, because the id is part of it.

Why there is no PATCH

Not a design preference. The v4 API has no working update for nutrition-log — tested against the live API, both kinds of entry:

EntryPATCH result
Anonymous (no food_ref) 500 INTERNAL
even with nothing changed
Identified (has food_ref) 400 Invalid argument:
data_point.name

updateMask is rejected on this endpoint as an unbindable query parameter. Sending {"dataPoint": {…}} returns Unknown name dataPoint, which proves the bare {"nutritionLog": …} body fsync already sends is the correct shape. And Google's own CLI registers no update operation for the type (pkg/types/registry.go:512, under a comment saying operations were confirmed by probing the live API). Create and delete both work, so an edit is expressed as both.

The create runs first

POST …/dataPoints ← new version POST …/dataPoints:batchDelete ← old id

The order is the safety property. If the create fails, nothing has changed and the original entry is still there. Deleting first would lose the entry outright the moment the create then failed.

The cost of that order is the other direction: if the create lands but the delete doesn't, a duplicate is left behind. fsync warns and names the old id, because nothing else will catch it — no file claims that id any more, so it can never surface as a pending delete.

Ids are not stable across edits. Anything referencing an entry by id — a note, a script, a bookmark — needs updating afterwards. If that matters more than the edit, delete and re-add by hand instead.

The five states a file can be in

Every command is just a transition between these. Which state a file is in is computed from three things: whether a file exists at all, whether it has an id, and whether its content still hashes to the digest recorded at last sync.

What each command touches

CommandNetworkWrites filesWhat it does
pull reads yes Fetches the window, writes new entries, refreshes unchanged ones, adopts orphans. Skips files you've edited.
status none no Classifies every file into the five states above. Flags an edited file as getting a new id.
push writes yes POSTs new entries; replaces modified ones (POST the new version, then :batchDelete the old); deletes entries whose files are gone, after asking. Writes back ids and digests. The only command that mutates Google.
add writes yes Writes a file from command-line args, then pushes it. --no-push writes only.
tidy none moves Files every entry into the day folder its start names.
total none no Sums a day from local files only.
config none no Prints where food_dir, ghealth and the index resolved to, and which file decided it.

push --dry-run prints the exact payloads and sends nothing. The food folder need not live beside the script — set food_dir in fsync.toml, or pass --food-dir / $FSYNC_FOOD_DIR.

The six ways this goes wrong

An edit changes the entry's id

by design

Because an edit is a replacement, the entry you get back is a different record with a different id, and the file is renamed. Nothing on disk is lost — but any note, script or link that pinned the old id now points at nothing. status says so before you push.

A replacement that half-lands

guarded

Create fails: nothing changed, the original entry is untouched, and push says which id was left alone. That is the whole reason create runs before delete.

Create lands, delete fails: a duplicate is left in Google Health. fsync warns and names the old id, because no file claims it any more — so it will never turn up as a pending delete. Remove it by hand.

Both sides changed

pull will not overwrite a file whose digest no longer matches — it skips and says so. You choose: push to send yours, or pull --force to discard yours and take the remote version.

Deleting by accident

A missing file is read as a deletion, so moving the folder or a bad rm could wipe remote records. push therefore lists every entry it is about to delete and waits for a y; with no terminal attached it refuses outright. --yes overrides. Until you push, the deletion is local only and pull --force restores the files.

A malformed file

Broken YAML or a missing required field is caught locally, listed as bad with the reason, and skipped. One bad file never blocks the others.

A create that loses its id

guarded

If the POST succeeds but the response carries no id, the entry exists remotely and your file doesn't know it. Pushing again would duplicate it. The file is marked orphan instead, push refuses to touch it, and pull matches it on time, name and calories to recover the id.

What's been exercised, and what hasn't

Run against the real API: the 7-day pull and repeated pulls (idempotent); a live create through add, whose id parsed on the first try; a live delete, confirmed gone from the API and not resurrected by the next pull; the no-terminal refusal and the --yes override; edit detection; new-file detection from any location; the day-folder migration; tidy; and total cross-checked against the API's own daily-rollup.

The replace path has now run for real. An entry's meal type was edited and pushed: the replacement returned 200 with the edited mealType and its macros intact, the old id returned 404, and the following pull settled to unchanged. The index and filename both moved to the new id.

What this replaced: this page used to list "a live PATCH" as the one untested path. It turned out not to be untested so much as impossible — PATCH fails for both anonymous and identified entries, which is why replacement exists at all. The earlier claim here that anonymous entries specifically could not be updated, and identified ones could, was wrong.

Still unexercised: both half-landed branches of a replacement (create fails; create lands but delete fails), and the orphan guard — all three are fallbacks that have only been triggered artificially.
