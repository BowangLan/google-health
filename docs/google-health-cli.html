Talking to Google Health from the command line

"Google Health" is now three separate systems. Which CLI path you take depends entirely on where your data physically lives — Google's cloud, or your phone.

The short answer

There is an official CLI, published by Google, and it ships Agent Skills for exactly this kind of setup:

# Go toolchain required git clone https://github.com/Google-Health-API/google-health-cli cd google-health-cli && go build -o ghealth . ./ghealth setup # OAuth, once ./ghealth list steps --format table ./ghealth daily-rollup sleep --days 7
But: the Google Health API only serves Fitbit and Pixel Watch data. If your numbers come from a Pixel phone or a third-party app, this API cannot see them at all.

For phone-side data the only route is Health Connect's own export — which happily turns out to be a plain, unencrypted SQLite file.

Where your data lives decides your path

Google split the old Google Fit brand in two: a cloud API for wearables, and an on-device store for everything else. There is no bridge between them from the CLI.

Route 1 — ghealth, the official CLI

Recommended Apache 2.0

Google published a first-party Go CLI for the Health API in mid-2026. It covers 40 data types, handles OAuth and token refresh for you, and — relevant to you specifically — ships two Agent Skills (SKILL.md files) so Claude Code can drive it directly.

# 1. build git clone https://github.com/Google-Health-API/google-health-cli cd google-health-cli && go build -o ghealth . # 2. one-time OAuth (writes ~/.config/ghealth/) ./ghealth setup # 3. read ./ghealth types # discover all 40 types ./ghealth list steps --format table ./ghealth list heart-rate --format csv > hr.csv ./ghealth daily-rollup sleep ./ghealth identity ./ghealth paired-devices # headless / another machine ./ghealth setup --non-interactive GHEALTH_ACCESS_TOKEN=... ./ghealth list weight --raw

Commands

list · get · create · update · delete · rollup · daily-rollup · reconcile · export-tcx · types · scopes · identity · profile · webhooks

Output

Simplified JSON by default; --format table, --format csv, --raw for untouched API responses. --dry-run prints the request.

Maturity

Early — ~256 stars, 7 commits on main. Official org, but young.

Route 2 — raw curl

Same API, no dependencies. Worth knowing even if you use the CLI, because the OAuth dance is where every setup actually gets stuck.

# a) consent URL — open in a browser, copy the ?code= from the redirect https://accounts.google.com/o/oauth2/v2/auth ?client_id=$CLIENT_ID &redirect_uri=https://www.google.com &response_type=code &access_type=offline &scope=https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly # b) code → tokens curl -X POST https://oauth2.googleapis.com/token \ -d "code=$CODE&client_id=$CLIENT_ID&client_secret=$SECRET" \ -d "redirect_uri=https://www.google.com&grant_type=authorization_code" # c) refresh later (access tokens last ~1h) curl -X POST https://oauth2.googleapis.com/token \ -d "client_id=$CLIENT_ID&client_secret=$SECRET" \ -d "refresh_token=$REFRESH&grant_type=refresh_token" # d) read curl -H "Authorization: Bearer $TOKEN" \ 'https://health.googleapis.com/v4/users/me/dataTypes/steps/dataPoints?page_size=10' curl -H "Authorization: Bearer $TOKEN" \ 'https://health.googleapis.com/v4/users/me/dataTypes/exercise/dataPoints?filter=exercise.interval.civil_start_time%20>=%20"2026-09-01T00:00:00"'

Base URL https://health.googleapis.com/v4. Data type names are kebab-case in paths (body-fat) but snake_case inside filters (body_fat) — an easy hour to lose.

Route 3 — MCP, if you want Claude to read it rather than you

Several community MCP servers wrap the same v4 API. They run locally; tokens stay on your machine and the only outbound calls go to Google. All are read-only and all are beta, because the API surface is still moving.

BerkKilicoglu/google-health-fitbit-mcp

Read-only, one-command install, explicitly local-first. The broadest metric coverage of the three.

jorgeschnura/google-health-mcp

Adds a computed recovery / readiness score on top of the raw reads.

davidmosiah/google-health-mcp

Local-first v4 server targeting Claude Code / Cursor.

Note: ghealth ships Agent Skills instead of an MCP server — for Claude Code that is arguably the better fit, since you get the CLI for scripting and the skill for conversation from one install.

Route 4 — Health Connect export → SQLite

Only path for phone-side data

Health Connect has no REST API and never will — it is deliberately on-device. But its backup/export feature writes a plain unencrypted SQLite database inside a zip, and it can be scheduled daily. That makes it a perfectly good CLI data source.

On the phone, once

Health Connect → Backup & restore → schedule export (daily / weekly / monthly) to a cloud folder. Produces Health Connect.zip.

Then, from anywhere

unzip "Health Connect.zip" sqlite3 health_connect_export.db ".tables" sqlite3 health_connect_export.db \ "SELECT * FROM steps_record_table LIMIT 5;" # or browse it properly datasette health_connect_export.db

Straight off the device — fits your Termux setup

You already run Termux on the Pixel with adb forwarding. Termux has sqlite3 and pkg install android-tools, so the whole loop can stay on-phone — no desktop in the path.

# pull the scheduled export off the device adb pull /sdcard/Download/"Health Connect.zip" . # or, entirely inside Termux pkg install sqlite unzip cd ~/storage/downloads && unzip -o "Health Connect.zip" sqlite3 *.db "SELECT COUNT(*) FROM steps_record_table;"

Community tooling worth a look if you want this automated rather than manual: kas-cor/healthconnect-export (daily JSON + Drive sync), angeloanan/HealthConnectExports, alexandershalin/health-connect-gate (pushes to your own HTTPS endpoint).

Four things that will bite you

Refresh tokens expire in 7 days while your OAuth consent screen is in Testing status. For a personal cron job this is the single biggest annoyance — you re-consent weekly unless you push the project to In Production, where refresh tokens last until revoked or ~6 months idle.
All Health scopes are "Restricted." Fine for you alone — add your own email to the test-user list, cap is 100 users. Going past that needs a third-party security review.
No Fitbit or Pixel Watch means no data. The v4 API is the Fitbit cloud with a new name. A Pixel phone alone gives you an empty API and a full Health Connect database.
Old OAuth tokens don't carry over from the Fitbit Web API. Anything you built against Fitbit needs a fresh Google consent — and after 30 Sep the old endpoints simply stop.

What I'd actually do

  1. If you own a Fitbit or Pixel Watch: build ghealth, run ghealth setup, and immediately publish the OAuth consent screen to In Production so refresh tokens stop expiring weekly. Its Agent Skills then give Claude Code direct access with no MCP server needed.
  2. If your data is phone-side only: skip the API entirely. Turn on the scheduled Health Connect export and point sqlite3 or datasette at the zip — you already have Termux and adb wired up on the Pixel, so this needs no new infrastructure.
  3. Either way, don't touch Google Fit or the Fitbit Web API. One is closed to new signups, the other dies in eight days.
