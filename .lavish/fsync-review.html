fsync · code review · 24 Sep 2026 · all 20 fixed

The sync model was sound.
Its bookkeeping wasn't.

The design — file is truth, digest for dirt, index for deletes, create-then-delete for edits — is the right shape for an API with no working update, and the comments earn their keep. The problems were all in one place: the index was rebuilt wholesale from disk, which quietly destroyed the one piece of state that only the index holds — “you deleted this”. Three bugs below all came from that.

All 20 findings are fixed in fsync. Every one was reproduced first, then re-tested after the fix: 36 assertions, 0 failures, covering each bug plus the normal pull / push / add / clone / tidy / total flows. Verified live afterwards against your real data — 28 remote, 28 local, in sync, nothing pending, index migrated byte-identical. The docs are updated too: README.md, CLAUDE.md (and AGENTS.md through its symlink) and docs/fsync-flows.html, with every new claim checked against the code's real output.

C1

A deletion survives exactly one command

Deleting a file is the only way to delete an entry, and the index is the only thing that remembers you did it. Both cmd_pull and cmd_push end by calling save_index(scan()[0]), which derives the whole index from the files that exist now. The deleted entry has no file, so its id is dropped — and a dropped id is indistinguishable from an entry you never had.

The rebuild · fsync:496

Reproduced · delete a file, then pull

# file deleted, nothing pushed yet pending deletes before pull: ['AAA'] $ fsync pull held 2026-09-24/1200--x--AAA.md deleted locally; run 'fsync push' to delete it pending deletes AFTER pull: [] $ fsync pull # the very next one new 2026-09-24/1200--x--AAA.md ← it's back
Same bug via push. Decline the delete prompt while any other entry is pending, and the save_index(scan()[0]) at the end of the push wipes the deletion too — “files stay gone locally but the remote entries remain” is true, but it will never ask again.

Fix · keep unresolved deletions in the index

With this, save_index is additive for tombstones and only delete_remote succeeding — or an explicit --force — clears one. The incremental write at fsync:894 can then go (N2), and so can the unlink at fsync:666 (N1).

C2

pull --force restores nothing

Two places promise it: the hold message in cmd_pull and the cancellation message in cmd_push. The hold branch never checks args.force — it continues before anything can be written, and the unlink that is guarded by --force runs after the loop, too late to matter.

The hold branch · fsync:629

Reproduced

$ fsync pull --force held 2026-09-24/1200--x--AAA.md deleted locally; run 'fsync push' to delete it remotely, or 'fsync pull --force' to restore it files after --force: [] # nothing restored

The entry does come back — on the next pull, because the index was wiped in the meantime. A two-step accident, not the documented behaviour.

Fix · one line

C3

Conflict detection that push never reads

sync_diff does real work to notice that both sides moved, and show_sync_diff says so in red rather than picking a winner. But cmd_push builds its work list from is_dirty(fm) alone — it never fetches the remote, so it cannot know. Push a conflicted entry and the remote change is deleted as part of the create-then-delete replacement, with an ok next to it.

The work list · fsync:874

Reproduced · local 150, remote 120

$ fsync sync ! 1200--x--AAA.md changed on BOTH sides kcal: 150 (here) vs 120 (remote) $ fsync push ok 1200--x--NEW1.md replaced AAA pushed 1 ok, 0 failed API calls: POST kcal=150 POST :batchDelete AAA ← remote's 120 is gone

Cheap fix

Have push refuse any entry whose stored sync.digest is older than what a sync last saw, i.e. record the last-seen remote digest in the index and compare. No extra fetch.

Honest fix

Fetch the affected window inside cmd_push before replacing anything, and hard-fail conflicted entries with the same red text sync uses. One request, and push stops being the one command that can destroy remote data unknowingly.

Related: M2 — because n_push deliberately excludes conflicts, sync --push on a conflict-only diff skips the push branch entirely and exits 0 without a word. Whichever fix you pick, that branch needs to say “1 conflicted, resolve by hand” and return non-zero.

M5

The YAML timestamp trap, which your own docs walk into

write_entry is safe: PyYAML quotes '2026-09-23T16:46:17-07:00' so it reads back as a string. A human — or an agent following CLAUDE.md's “set start to the requested date” — writes it unquoted, and YAML resolves it to a datetime. digest() stringifies with default=str, which renders a datetime with a space instead of T.

digest(string start) = 118b91e891e03b8f digest(datetime start) = ca6668e02f532b89 ← same instant, different hash yaml.safe_load("start: 2026-09-20T12:00:00-07:00")["start"] -> datetime.datetime(2026, 9, 20, 12, 0, tzinfo=...)

The local digest is self-consistent, so nothing looks dirty — but it never matches digest(remote_to_fm(dp)), so sync reports the entry as changed in Google Health on every run, forever, with a diff that reads start: 2026-09-20 12:00:00-07:00 -> 2026-09-20T12:00:00-07:00. One-line fix: coerce in read_entry, next to the other normalisation.
